# unity-core — one package for the generic Unity GameComponents (PARKED until Racer nears release)

Review §3.4, owner 2026-09-27: plan it. Multi-project: dcm-client (Crossle, production), racer (Unity),
CommonClientGame submodule. Paths relative to `/Users/fkavum/Documents/project/`.

## 1. State (2026-09-27)

- Both projects are Unity `6000.0.60f1`.
- dcm-client shares with dcm-game-server through the `CommonClientGame` submodule (`dcm-sub-client-game`, branch
  `dev`, pinned at the same commit in both). Racer does **not** use it: no `.gitmodules`.
- Racer's shared code is hand-ported from dcm-client with `// Ported from dcm-client Assets/GameComponents/…` headers:
  `GameComponents/Kvp` (10 scripts, differ only by namespace `DontCrossMe.GameComponents.Kvp` → `GameComponents.Kvp`
  + header), `HttpShared/Kvp` DTOs (12 files, byte-identical), `HttpSender` (211 vs 273 lines, diverged),
  `AppConfig` (diverged), `EnvironmentInfo` (racer only). Racer-only GameComponents: Core, Inventory, KvpSqlite,
  LoadingWidget, SceneManagement, PopupSystem (no same-path counterpart in dcm-client).
- dcm-manager's rule already says GameComponents are "the unit of portability — isolated, plug-and-play systems each
  with a `XxxModule.cs`", which is exactly a package boundary.

## 2. Options

| | A. Grow `CommonClientGame` | B. Local UPM package `com.dcx.gamecomponents` | C. Keep porting by hand |
|---|---|---|---|
| Mechanism | Racer adds the submodule; generic GameComponents move into it | New repo `dcx-unity-core/` with `package.json`, `Runtime/`, `Editor/`, asmdefs; both projects reference it via `"com.dcx.gamecomponents": "file:../../dcx-unity-core"` in `Packages/manifest.json` | status quo |
| Cost | CCG is meant to be "communication-purpose code only" (dcm-manager Modularization Principles) — GameComponents would break that boundary; the game server would carry Unity-only code | One-time namespace unification (`DontCrossMe.GameComponents.*` → `Dcx.GameComponents.*`) touches Crossle; asmdef discipline needed | drift, already visible in `HttpSender` |
| Fit with the server-side rule | — | Same shape as dcm-web ownership: the package is the upstream, a project-specific variant is a fork with a suffix, "does it exist in the package?" is the ownership test | — |

**Proposal: B**, started only when Racer has a release date, in a Crossle release window (the namespace change is the
one moment it touches the live game). Until then **C, with one rule**: every ported file keeps the `Ported from` header
(already the case) so the extraction is a grep.

## 3. Scope of the first package (when it starts)

`Kvp` (+ `HttpShared/Kvp` DTOs, generated by dcm-web — the generator gains a `package` target), `Config`
(`AppConfig`, `EnvironmentInfo`), `HttpClient` (`HttpSender` reconciled: racer's `IHttpSender` split + dcm's
multipart support), `PopupSystem`, `LoadingWidget`, `Localization` if generic. Crossle-specific pieces stay in
`Assets/DontCrossMe/`. Racer's `KvpSqlite` becomes the package's offline provider (`racer-manager` offline-first rule).
